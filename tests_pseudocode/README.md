# Pseudocode test architecture

This directory is the **test design contract** for the implementation work objects in `historical_globe_pseudocode/`.

The goal is not to guess a final JavaScript/TypeScript test framework now. The goal is to specify enough observable behavior that a later low-capability TEST-WRITER agent can translate each test seam into the repository's concrete test stack without rediscovering intent.

## Why tests are also split by seam

Every product work object has a matching `@test-spec` / `@test-seam` block. A conductor may therefore produce two independent packets:

1. **TEST-WRITER packet** — translate the visible pseudocode tests to concrete tests/fixtures.
2. **IMPLEMENTER packet** — implement the product seam and run the visible tests.

A benchmark evaluator additionally runs evaluator-generated cases derived from the oracle families in `evaluator-oracles.pseudo.ts`. Concrete hidden seeds/fixtures MUST NOT be included in worker packets.

## Test layers

Use the cheapest layer that proves the contract:

- `STATIC` — imports, package manifests, forbidden dependencies, file/path constraints.
- `UNIT` — deterministic pure behavior.
- `PROPERTY` — generated inputs / metamorphic invariants.
- `COMPONENT` — UI/component behavior with fake adapters/engines.
- `INTEGRATION` — multiple project seams with controlled dependencies.
- `DSH_INTEGRATION` — real DSH public extension/session seams.
- `BROWSER_E2E` — actual Historical Globe profile and visible interaction.
- `CLEAN_ENVIRONMENT` — fresh checkout/profile bootstrap and hidden-local-dependency falsification.

Do not promote a UNIT contract to BROWSER_E2E merely because the product has a browser UI.

## Delimiters

```text
/* @test-spec
{ valid JSON metadata }
@end-test-spec */
/* @test-seam HG-AREA-NNN:begin */
... visible pseudocode tests ...
/* @test-seam HG-AREA-NNN:end */
```

The test seam is suitable for a worker packet. The evaluator oracle is not.

## Test-spec metadata

```json
{
  "for": "HG-AREA-NNN",
  "layers": ["UNIT"],
  "fixtures": ["fixture names"],
  "requiresRealDSH": false,
  "requiresBrowser": false,
  "oracleFamily": "HG-AREA-NNN-ORACLE"
}
```

## TEST-WRITER contract

A TEST-WRITER:

- receives only the target `@test-seam`, dependency signatures, and the minimum fixture contracts;
- translates assertions faithfully into the chosen concrete framework;
- MUST NOT weaken, delete, reinterpret, or replace an assertion because implementation is inconvenient;
- MUST NOT inspect the implementation under test when writing a benchmark's initial visible tests unless the test task explicitly says `whiteBoxAllowed=true`;
- may add framework plumbing but not new product behavior;
- reports `BLOCKED_CONTRACT` if the pseudocode is not implementable as an objective test.

Tests generated by a worker are not trusted merely because they run. The evaluator validates that the concrete tests preserve the pseudocode assertions.

## Hidden/evaluator tests

`evaluator-oracles.pseudo.ts` defines **families of valid additional cases**, not the concrete hidden cases. During a benchmark run:

1. evaluator chooses an unrevealed seed;
2. deterministic generator materializes cases from the oracle family;
3. worker attempt is scored;
4. seed may be disclosed only after scoring if desired for reproducibility.

This is not adversarial secrecy for its own sake. It prevents a model from passing by hard-coding the few visible examples while still making the benchmark scientifically reproducible.

## Benchmark success

A work-object attempt is a functional PASS only if:

- all mandatory visible tests pass;
- all generated evaluator cases pass;
- architecture/static constraints pass;
- no forbidden scope/dependency changes occurred.

Keep sub-scores for diagnosis, but do not average failures into a misleading overall pass.

## Important distinction

A failed test can mean one of three things:

1. implementation defect;
2. concrete test translation defect;
3. pseudocode contract/design defect.

The evaluator must classify these separately. A strong reference-model canary should be used to validate new test specs before they are admitted into model-comparison benchmarks.
